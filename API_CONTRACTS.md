# API LIGHT FORGE

Доступны Geometry API v1, Quick RFQ и анализ фотографий v1. Машиночитаемый контракт в [openapi.yaml](openapi.yaml). Генерация из Zod выполняется командой `npm run openapi`.

## Геометрия

`POST /api/geometry/resolve` принимает `Composition` как JSON. Ответ `ResolvedComposition` содержит локальную форму каждого корпуса, мировые координаты известных точек, отметки низа и верха, потолочные основания и отдельные результаты тросов и ремней. Запросы до 1 МиБ. Ответы `400` обозначают ошибку JSON, `413` — превышенный лимит, `415` — другой тип содержимого, `422` — нарушение схемы или связей. При `422` UI привязывает массив `issues` к полям формы.

- `src/geometry/schema.ts` экспортирует типы `Composition`, `Element`, `Canopy`, `Point`, `Shape`.
- `src/geometry/result.ts` экспортирует типы `ResolvedComposition` и `ResolvedValue`.
- `src/geometry/resolve.ts` экспортирует `resolveComposition` и функцию перевода осей `engineeringToThree`.
- `src/geometry/examples.ts` даёт `createMylineComposition()` с фактическими исходными данными и `createGeometryExample()` с тестовыми размерами троса, ремня, кольца, дуги и профиля.
- `src/storage/compositions.ts` экспортирует `openCompositionStore`, `importComposition`, `exportComposition`. В браузере хранение на уровне origin. При переходе на другой origin переносите композицию JSON-файлом.

Геометрия проверяет уникальные ID, наличие адресуемых креплений, корректные внутренние диаметры, дуги до 180° и выходы внутри основания. Некомплектные данные возвращаются со статусом `unknown`. Для UI полезны `pathLength`, `cutLength`, `formula` и `points`. Формула хранит смещение и коэффициенты `ceilingFromFloorMm` и `tabletopFromFloorMm` отдельно для каждой компоненты отрезка.

`GET /api/health` — состояние локального сервиса.

## Quick RFQ

`POST /api/rfq/quick?format=text&lang=en` принимает JSON `{ project, composition? }`. Возвращает `{ language, text }`. Языки — `en`, `zh` и `en-zh`. Снимок `Project` описан в `src/domain/project.ts`. Опциональная композиция должна ссылаться на тот же проект и согласовываться по размерам, количеству и уровням. Для совпадающих идентификаторов монтажных точек также сверяются координаты X и Y, заданные в обоих источниках. При расхождении API возвращает `422 project_geometry_conflict`.

`POST /api/rfq/quick?format=pdf&lang=en-zh` возвращает PDF для предпросмотра и скачивания. Для проекта с фотографиями передавайте `multipart/form-data` с текстовым полем `input` (JSON снимка) и полями `photo:<id>` (оригинальные байты каждого файла из `project.photos`). Проект без фото можно передать JSON. Выбранный файл `primaryPhotoId` отображается первым. Поддерживаются JPEG, PNG и WebP, до 8 файлов, 12 МиБ на файл и 32 МиБ суммарно. Ограничения декодирования — до 60 Мп на фото и 120 Мп суммарно. API возвращает `422 invalid_photo` для отсутствующего или неподдерживаемого файла.

Для интерфейса используйте `quickRfqForm(snapshot, composition?)` из `src/storage/projects.ts`. Передайте форму в `fetch`; браузер сам задаст multipart boundary. Успешный ответ преобразуйте в Blob, создайте URL через `URL.createObjectURL` и переиспользуйте тот же PDF для предпросмотра и сохранения. Освобождайте URL после замены или ухода с экрана. При `503` покажите ошибку PDF-движка и предложите повторить запрос.

`openProjectStore()` сохраняет снимок и исходные Blob в IndexedDB. `exportProject()` и `importProject()` предоставляют переносимый JSON с оригиналами.

С привязанной композицией Quick RFQ показывает известные габариты потолочных оснований и отдельно выводит длину пути и длину заготовки с припуском для каждого троса и ремня. Расчётные значения предназначены для оценки стоимости и требуют подтверждения перед изготовлением.

Quick RFQ является предварительным запросом. Неуказанные монтажные и электрические данные явно отмечаются для подтверждения. Сервис не требует ключей внешних API.

## Анализ фотографий v1

`GET /api/photo-analysis` возвращает `apiVersion: 1`, доступный режим и лимиты. `POST /api/photo-analysis` принимает `multipart/form-data`. Поле `input` содержит JSON `{ "photos": [...] }` с метаданными выбранных файлов в формате `Photo`. Каждому элементу соответствует поле `photo:<id>` с исходным файлом. Передаются только выбранные фото. Заголовки multipart устанавливает браузер.

| Поле ответа | Значение |
|---|---|
| `mode: "metadata_only"` | Сервер проверил формат и размеры растра из файла. `suggestions` всегда пуст. Покажите «Распознавание ещё не подключено» и оставьте доступным ручной ввод. |
| `mode: "visual_analysis"` | Подключённый движок может вернуть подсказки. Пустой список в этом режиме означает, что подходящих подсказок нет. |
| `photos` | Исходные метаданные и `widthPx` / `heightPx` в пикселях. Это размеры растра в файле, которые могут относиться к его ориентации до поворота EXIF. |
| `suggestions` | Оценочные `productKind`, `material` и `lightDirection`. Каждая подсказка содержит `id`, `photoId`, `confidence`, `source: "estimated"` и `payload`. |
| `summary`, `warnings` | Необязательные строки для отображения. |

Размеры изделия, уровни монтажа, мощность, световой поток, CCT и CRI в визуальных подсказках v1 отсутствуют. Подсказки никогда не применяются автоматически. В интерфейсе можно принять, исправить или пропустить предложение. Метаданные фото и оригиналы остаются отдельными от спецификации проекта.

Для адаптера Antigravity используйте общий тип ответа и HTTP-клиент. Передавайте `AbortSignal`, чтобы отменить запрос при смене выбранных фото.

```ts
import { requestPhotoAnalysis } from '@/photo-analysis/client';

const photoAnalysisProvider: PhotoAnalysisProvider = {
  label: 'LIGHT FORGE',
  analyze: ({ snapshot, photoIds, signal }) => requestPhotoAnalysis(snapshot, photoIds, signal),
};
```

Чтобы панель могла различать режимы, сохраняйте `mode` из ответа, даже если отображаемый список подсказок пуст. Лимиты совпадают с Quick RFQ: JPEG, PNG, WebP, до 8 фото, 12 МиБ на файл, 32 МиБ суммарно и до 60 Мп на фото / 120 Мп суммарно. Маршрут работает в `metadata_only` без регистрации движка, ключей и внешних запросов. Рабочий визуальный движок подключается отдельно после согласования поставщика и расходов.

### Локальный визуальный движок Ollama

После запуска Ollama 0.12.7+ с отключённым облаком установите локальную модель `qwen3-vl:2b-instruct` командой `ollama pull qwen3-vl:2b-instruct`. Размер модели около 1,9 ГБ. Запустите сервер LIGHT FORGE с `LIGHT_FORGE_PHOTO_ENGINE=ollama` в окружении. Ollama должна слушать `127.0.0.1:11434` на том же хосте, где запущен Next.js. В настройках Ollama можно отключить облачные функции через `OLLAMA_NO_CLOUD=1`.

Локальный движок определяет только видимый тип светильника и выдаёт максимум одну оценочную подсказку на фото. Для неопознанного типа возвращается пустой список. Сервер передаёт выбранные фото локальной модели и проверяет её JSON. Повторный запрос с теми же байтами может использовать кэш подсказок в памяти до 10 минут. Кэш не хранит фотографии. Один экземпляр сервера выполняет один анализ за раз. При занятости, недоступности модели или тайм-ауте API возвращает `503 engine_busy`, `503 engine_unavailable` или `503 engine_timeout`. Невалидный ответ модели возвращает `502`. Без флага сервер остаётся в `metadata_only`.

Документация [Ollama Chat API](https://docs.ollama.com/api/chat), [локальный режим](https://docs.ollama.com/faq) и [модель Qwen3-VL](https://ollama.com/library/qwen3-vl%3A2b-instruct).
